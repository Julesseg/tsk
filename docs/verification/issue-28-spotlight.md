# Spotlight tasks (#28)

Spotlight indexes unfinished (`pending`) tasks by a namespaced, canonical task UUID. Waiting/blocked tasks remain eligible. Recurring templates, completed/deleted/unknown-status tasks and blank descriptions are excluded. The searchable projection contains the description, project and tags; opaque attributes and annotation contents are not copied into the system index. Core projection and routing preserve task UUIDs and raw task attributes.

Core `TaskManager.reconcileSpotlight(using:)` reads current tasks and writes the full eligible projection through `TaskSpotlightIndex`. `resolveSpotlight(identifier:namespace:)` validates the exact namespace/UUID and rereads storage. A completed result opens its current completed state; missing/deleted/foreign/malformed results show an unavailable state. Routing never finds a task by title or falls back to another task. SwiftUI handles the real `CSSearchableItemActionType` activity and `CSSearchableItemActivityIdentifier`, then opens the common task detail with native iPhone/iPad presentation. The destination revalidates when task state changes.

Native `CoreSpotlightTaskIndex` uses a named `CSSearchableIndex`, scoped domain deletion and real indexing completion callbacks. It does not delete a default/global index. A full replacement removes completion/deletion entries and updates titles under the same UUID. OS replacement is not a transaction: a failed delete/index sequence can temporarily leave missing or old results; persisted error state and explicit retry remain available. OS search/cache appearance is not promised to be immediate.

`SpotlightTaskEffect` is composed with notification effects in the central native factory for iOS participants. Core awaits effects after durable mutations and after releasing the semantic mutation lease; successful/no-change and partial synchronization paths also reconcile. A separate shared-directory admission covers fresh task read through the platform write, preventing stale concurrent managers from replacing a newer projection. Ordinary task writes are not held behind OS indexing. Index errors do not turn a durable task save into failure. Shared status records are atomic, first-unlock protected on iOS and mode0600. The app reconciles on opening/foreground and offers status, query and retry in Spotlight settings. Main-app index queries expose errors and explicitly distinguish API verification from system search UI. Host/CLI factories perform no default OS effects.

App/extension execution, OS throttling, index loss and background opportunity can delay updates; foreground/reopen/manual retry rebuild the scoped projection. Task-change revisions remain invalidation hints, not guaranteed background delivery. No independent indexing extension or guaranteed background reindex service is claimed. Index access from each extension and real system discovery remain separate runtime checks.

Apple references: [indexing app content](https://developer.apple.com/documentation/corespotlight/adding-your-app-s-content-to-spotlight-indexes), [searchable-item routing](https://developer.apple.com/documentation/corespotlight/cssearchableitemactiontype), [querying app content](https://developer.apple.com/documentation/corespotlight/searching-for-information-in-your-app).

## Verification boundaries

Public Core tests verify eligibility, stable identity across edits, completion removal, exact stale/current UUID resolution, foreign namespace rejection, preserved raw fields and index errors. Native tests use real TaskChampion storage to verify concurrent writes while a controlled index is blocked, latest-state reconciliation, durable success despite effect failure, persisted status/retry, and actual encrypted received completion/deletion through the shared post-commit path. Controlled index adapters verify orchestration, not Spotlight OS success.

A uniquely named host synthetic `CSSearchableIndex` attempt returned `CSIndexErrorDomain -1000`; scoped cleanup was attempted and no successful host indexing is claimed. The diagnostic remains opt-in with `TSK_SPOTLIGHT_REAL_INDEX_TEST=1`. It does not touch personal/default indexes. Normal headless native tests must not pretend to have an installed app's Spotlight identity.

Unconditional canonical iPhone/iPad `SpotlightUITests` exercise the installed app's real `CSSearchQuery`, actual Home-screen Spotlight query/result tap to exact persisted UUID, local completion removal, an explicitly injected stale native index entry opened through the real system UI, and actual encrypted peer completion received by the app. Test cleanup clears only the UUID fixture domain, then stops before foreground reindex. ShareFIRST, widget, Calendar/Reminders evidence harvesting and the real sync peer wrapper remain intact. These runtime scenarios and screenshots were written but not executed locally: no simulator was booted. A system UI failure must remain a failure, independent of an API query passing.

The report lists uncaptured system/permission/error/iPad states and missing Before/After workspace comparisons. No physical-device, keyboard, personal-account, unrestricted background, visual acceptance or release-provisioning proof is implied by generic compilation.
