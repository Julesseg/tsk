# Spotlight tasks (#28)

Spotlight indexes unfinished (`pending`) tasks by a namespaced, canonical task UUID. Waiting/blocked tasks remain eligible. Recurring templates, completed/deleted/unknown-status tasks and blank descriptions are excluded. The searchable projection contains the description, project and tags; opaque attributes and annotation contents are not copied into the system index. Core projection and routing preserve task UUIDs and raw task attributes.

Core `TaskManager.reconcileSpotlight(using:)` reads current tasks and writes the full eligible projection through `TaskSpotlightIndex`. `resolveSpotlight(identifier:namespace:)` validates the exact namespace/UUID and rereads storage. A completed result opens its current completed state; missing/deleted/foreign/malformed results show an unavailable state. Routing never finds a task by title or falls back to another task. SwiftUI handles the real `CSSearchableItemActionType` activity and `CSSearchableItemActivityIdentifier`, then opens the common task detail with native iPhone/iPad presentation. The destination revalidates when task state changes.

Native `CoreSpotlightTaskIndex` uses a named `CSSearchableIndex`, scoped domain deletion and real indexing completion callbacks. It does not delete a default/global index. A full replacement removes completion/deletion entries and updates titles under the same UUID. OS replacement is not a transaction: a failed delete/index sequence can temporarily leave missing or old results; persisted error state and explicit retry remain available. OS search/cache appearance is not promised to be immediate.

`SpotlightTaskEffect` is composed after the awaited notification effect in the central native factory. Notification acceptance/cancellation and immutable sync-receipt semantics stay awaited after the semantic mutation lease releases. Spotlight instead persists a pending task revision under a short metadata lease, coalesces one retained worker per directory/owner and returns without waiting for index admission or an OS callback. A callback that never arrives can leave Spotlight pending while durable create/edit/completion and successful synchronization return their real result. Enqueue or index errors remain separate integration warnings, never a retry-create failure.

Only the containing app owns the production index worker and confirmed receipt. Ordinary Share/Widget participants publish shared pending work; an App Group and equal index name do not establish shared Core Spotlight ownership. The running app schedules work when participant task changes arrive, on opening/foreground and through explicit retry. An extension may finish before indexing can execute; the next app opportunity retries. No indexing maintenance extension or guaranteed background service is claimed. Host/CLI factories perform no default OS effects; native harnesses inject an explicit owned worker and controlled index.

The worker retains the separate cross-process index lease through both real callbacks. It captures the task revision before reading the Core projection and confirms only that revision. New changes coalesce into a fresh projection after completion; they are never queued as old task snapshots. Pending return does not release admission, cancel submitted operations or allow takeover. A real callback error leaves dirty work and a visible warning for a later opportunity. Explicit retry carries a separately admitted durable repair token, so an unchanged task revision can still repair a reset index. Publication/enqueue warnings also invalidate that token; an older manager cannot clear them and certify an old projection against an unchanged revision. Only a matching real worker confirmation clears the warning. Status is atomic, first-unlock protected on iOS and mode0600; pending and old journaled count/time are distinct. Journaling acknowledgement alone is not search visibility.

After worker process death the lease releases, but an unconfirmed attempt stays on disk. A later owner retries fresh storage. This does not prove Apple's already-submitted operation was cancelled or establish strict cross-crash ordering inside its service; current-storage validation on every result open remains the safety boundary. No timeout-unlock/default-index fallback is used.

Apple references: [indexing app content](https://developer.apple.com/documentation/corespotlight/adding-your-app-s-content-to-spotlight-indexes), [searchable-item routing](https://developer.apple.com/documentation/corespotlight/cssearchableitemactiontype), [querying app content](https://developer.apple.com/documentation/corespotlight/searching-for-information-in-your-app).
