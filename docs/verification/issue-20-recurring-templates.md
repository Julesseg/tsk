# Recurring templates and external generation

TaskManager creates a recurring template through `createRecurringTemplate(RecurringTaskDraft)` and exposes `recurringTemplates()`. A template has a new UUID, trimmed nonblank description, a valid positive first due instant, the validated recurrence spelling, `status=recurring`, `rtype=periodic`, and normal creation/modification timestamps. Its mask, parent, and occurrence index are initially absent. Controlled recurrence/status/history fields in the input attribute map are rejected rather than copied or silently repaired. Project/tag/priority validation applies and unfamiliar fields are retained. Optional scheduled/wait/until values must be valid positive Unix seconds.

The first due must fit Taskwarrior's supported date range and leave room for the next period. Rules must make positive progress. Numeric calendar-month/quarter quantities must be whole numbers; unsafe oversized periods are rejected. The raw rule is retained. For example, `monthly`, `2m`, `P2M`, `P3M`, `quarterly`, and `2months` must not be normalized to one representation: the pinned generator uses different calendar or fixed-second branches.

`TaskwarriorDuration` is the common lexical duration module used by recurrence validation, typed attributes, and relative filter dates. Its `seconds` value follows Taskwarrior's fixed duration conversion; it is not a recurrence schedule. Recurrence validates the source spelling separately, including calendar branches and the generator's fixed-interval integer limit. The app does not calculate or create occurrence records.

The app has a native Recurring templates list, creation form with explicit first due and raw rule/frequency choices, and inspection in task details. It explains that the designated recurrence-enabled Taskwarrior client must synchronize, run a generation-triggering report, and synchronize again. Use one generator; an offline generator cannot deliver new occurrences. Calendar rules use that generator's time zone. Templates stay separate from the ordinary unfinished list; returned pending occurrences appear there and in their relevant date views.

TaskRecurrenceInspection distinguishes templates, generated occurrences, and unrecognized data. It preserves malformed fields and reports unsupported values. Ordinary mutation/annotation/dependency routes remain guarded for recurring data, including additional recurrence markers such as rtype/template/last. Occurrence editing and compatible completion are deliberately reserved for their dedicated actions; an ordinary status or property edit cannot bypass the guard.

## Source contract

The implementation and tests are pinned to Taskwarrior 3.5.0 (`3419d5ba1e6a780fbbb0a8d68d8fd31e675c1bf8`) and TaskChampion 3.1.0. Relevant primary sources: [template validation/defaults](https://github.com/GothenburgBitFactory/taskwarrior/blob/v3.5.0/src/Task.cpp), [generation and masks](https://github.com/GothenburgBitFactory/taskwarrior/blob/v3.5.0/src/recur.cpp), and [fixed duration lexer/conversion](https://github.com/GothenburgBitFactory/libshared/blob/86935551e0faa56ed14c52802a23280a593df338/src/Duration.cpp). The encrypted sync server stores history; neither it nor TaskChampion performs Taskwarrior command validation or occurrence generation.

The real external sequence is template creation in native storage → encrypted synchronization → designated Taskwarrior sync → generation-enabled report → Taskwarrior sync → native synchronization and persistent reopen. The generator fixture uses isolated data/configuration, Taskwarrior 3.5.0, explicit POSIX Central European DST rules (`CET-1CEST,M3.5.0/2,M10.5.0/3`), recurrence.limit=3, and a real owned TaskChampion sync server 0.7.1. Future 2094/2096 anchors keep this real-clock test from accumulating a historical backlog; they have the same relevant calendar boundaries as the independently verified 2027/2028 examples. It checks that sync alone creates no occurrences, that generated UUIDs link to the original template and mask positions, that unfamiliar fields and scheduled/wait offsets survive, and that another report/sync creates no duplicate positions.

Verified generator boundaries include weekly, daily across spring DST, monthly January-31 clamp drift, numeric `2m`, ISO `P2M` and `P3M`, quarterly, yearly leap-day drift, and an Until date between weekly occurrences. In particular, real `P3M` loses time to generator-local midnight, while `quarterly` preserves the wall clock. ISO-month matching precedes the named quarterly/semiannual aliases in this source; do not assume `P3M`/`P6M` are exceptions to that branch. The generator can include the first occurrence beyond Until. Its waiting-mask expiry behavior also follows the external implementation; the app does not silently rewrite the result.

## Evidence boundaries

Core tests use the public TaskManager seam for valid initialization, rejected dates/rules/controlled fields, raw spelling preservation, inspection, and unchanged occurrence guards. Native tests execute the complete real encrypted generator sequence and test template creation's automatic synchronization separately. No personal client, taskrc, server, or account is used.

RecurringTemplateUITests creates/validates/inspects/reopens a template through the real app/Core/native store. Its occurrence display test uses TaskwarriorRecurringFixture.json, recorded from the actual 2027/2028 Europe/Paris native return sync before moving the generator regression anchors into the future, and installs that data only with a DEBUG launch flag and an isolated test replica name. The fixture does not evaluate a recurrence or claim live generation inside the UI test. It tests native presentation, parent navigation, persistence, and guarded occurrence actions independently from the live native generator test. iPhone/iPad canonical lanes retain screenshot attachments.

Signed generic simulator build-for-testing compiles the app, test target, and recorded resource without booting a simulator; extracted App Intent metadata and embedded shared-group entitlement remain checked. Actual iPhone/iPad UI execution/captures, device provisioning, a user's designated generator, and long-running background delivery remain separate acceptance evidence. The release lane's required App Group capability is unchanged; an unconfigured signing profile must fail rather than lose the entitlement or use private fallback storage.
