# Task notifications (#30)

Pending ordinary tasks and occurrences derive alerts from `scheduled` and `due`. Equal effective times use one combined request; distinct times remain separate. Recurring templates, completed tasks and deleted tasks do not produce alerts. Waiting and dependency state do not erase a real task date. Raw task attributes, UUIDs and unfamiliar fields are unchanged by preferences or reconciliation.

Midnight replacement defaults to 09:00 in the current device time zone. Disabling it preserves the exact stored instant. A configurable time in a DST gap uses the next valid time; a repeated time uses the first occurrence. Nonmidnight dates remain absolute. Actual iOS registrations use absolute Gregorian UTC components. Foreground, task revisions, significant clock changes and time-zone changes reconcile fresh dates when the process can execute. A closed process cannot react immediately to a later time-zone change.

The common iOS participant factory injects awaited post-commit effects into every manager used by the app, AppIntents, share extension and widget. Durable task mutation and change publication finish under their owned semantic scope; that scope releases before notification IPC. A later return cannot release a newer mutation's scope. Reconciliation takes a separate cross-process notification lease, reads current tasks briefly under semantic admission, then performs system IPC without holding task admission. It rereads tasks after IPC and retries a changed plan up to three times. Continued changes remove the just-registered snapshot and report a retryable warning. SQLite and the system notification daemon are separate stores; no distributed atomic commit is claimed.

A notification failure cannot turn a durable create into a failed save or encourage duplicate creation. The saved task identity is returned; notification settings and the workspace attention action expose registration warnings and reconciliation retry. Permission is requested only from an explicit settings action. Denied/revoked permission cancels this application's owned pending requests and leaves task management usable. Host macOS test factories and pure Core managers have no default platform effects; explicit owned adapters are required for platform testing.

Pending readback, decoded request payload and actual next trigger must match before reporting a registration. Replaced task dates cancel the old request before adding the new one; a failed replacement does not retain a known wrong alert. Capacity is not hardcoded. The coordinator attempts registration, observes the retained count and prioritizes the nearest future requests if the OS rejects or evicts requests. Every unregistered future request remains visible in the report. Unrelated identifiers are never removed. No modern capacity count is established by source compilation or Core policy tests.

Device-local `task-notifications.json` uses atomic protected writes and a notification-specific lock. Malformed state produces an integration error and is preserved. Original event identity is task UUID, planned/due role and stored epoch seconds; request identity additionally reflects current display grouping. Accepted retained events record their effective delivery opportunity independently of later grouping or preferences. Once that opportunity has passed, moving a fallback time cannot repeat the same original constituent event. This is repeat suppression, not proof of exactly-once delivery. Notification Center can omit dismissed delivered alerts.

# Verification

Core tests cover distinct/combined dates, unchanged stored attributes, current-zone midnight behavior, DST gap/fold, excluded statuses, nearest retained registrations, cancellation/date replacement, denied permissions, original-event repeat suppression and owned post-commit reentrancy. Native tests use the real TaskChampion bridge/storage and admission, reopen saved records, preserve byte-distinct unknown attributes and demonstrate that a corrupt integration ledger does not fail the durable task save. They do not touch the host user's notification center.

`TaskNotificationUITests` runs in the canonical disposable iPhone/iPad lane. The installed app explicitly requests real permission, registers a fresh wall-clock alert, reads pending state, terminates before its trigger and relaunches without reseeding to inspect actual delivered identifiers. Another action attempts 100 actual registrations and records every acceptance/error plus retained IDs, then removes only its owned probe requests. The real reschedule/complete AppIntent `perform()` methods must replace/cancel pending alerts before returning. A system Settings revocation scenario proves that a task still saves durably under actual denial. These are test implementations until a successful canonical run supplies runtime evidence.

Evidence is written to app Documents `notifications-fixture-<UUID>.json` and harvested alongside EventKit/widget JSON by `run-ui-tests.sh`. Existing Share-first and main result bundles remain separate. XCUITest screenshots cover registration before termination, delivered readback, capacity, mutations and denial. Local simulator execution was intentionally not used under the shared machine's disk constraint. Physical device, Focus/locked-device behavior, notification presentation and unscheduled background opportunities require separate evidence.

# Ticket #31 boundary

The [#31 implementation](issue-31-missed-notifications.md) extends this foundation with an immutable native successful receipt, settled versus partial knowledge, exact local-write context, a durable retry/attempt/acceptance ledger and immediate missed alerts. Existing #30 accepted/known records are preserved conservatively. No semantic lease spans network waits; the ordinary future registration and cancellation policy remains shared with all participants.
